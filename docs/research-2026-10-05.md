# 本地直播观看软件调查

调查日期：2026-10-05（香港时间）；斗鱼短号问题于 2026-10-06 修正并复测。目标系统：Windows 11 25H2。

## 结论

建议正式产品内置成熟播放引擎（首选评估 libmpv，备选 libVLC），同时允许选择外部 PotPlayer。原型阶段优先验证“平台解析器 → 本机 HTTP 流地址 → 外部播放器”。Windows 系统默认播放器不作为主播放路径。

画质由平台实际返回的流决定。更换播放器或本机转发不会提高源流码率。接口的画质说明、可选列表与当前实际返回档位必须分别处理。

## 调查方法与边界

- 已查阅现行 Streamlink 平台插件、播放器适配代码、mpv 手册和微软播放组件文档。
- 已直接请求指定公开房间及公开补充样本；没有读取浏览器 Cookie，没有登录任何账号。
- 已读取短时 FLV 字节流、解析容器元数据及音视频标签，并检查 HLS 播放列表和一个媒体分片。
- 尚未完成音视频解码、画面/声音检查、PotPlayer/系统默认播放器实播、30–60 分钟稳定性测试、登录前后对比和硬件解码验证。
- 项目隔离的 PyAV 解码测试依赖下载长时间未完成，已停止下载，因此不能把容器读取成功当作解码播放成功。
- 本机注册表的 DisplayVersion=25H2、CurrentBuildNumber=26200；这不能代替实际播放器兼容性验收。

## B 站：用户指定短房间号 35

短号对应实际房间号 21622811，测试时 live_status=1。

调用 getRoomPlayInfo，请求 protocol=0,1、format=0,1,2、codec=0,1、platform=web，并分别请求 qn=10000、400、250。

所有请求返回 code=0，但全部流的 current_qn 均为 250。accept_qn 虽列出 [10000,400,250]，并不表示匿名请求成功得到原画或蓝光。全局画质字典中的 2K/4K/杜比也不能作为该房间可播放能力的证据。

接口列出 HTTP-FLV、HLS TS、HLS fMP4，每种均有 AVC/HEVC；实际读取仅测 AVC：

| 流 | 本次观察 |
|---|---|
| HTTP-FLV / AVC | HTTP 200，FLV 文件头正确，元数据 1280×720、30 fps；最后一次读取约 17.9 秒媒体时间，含音视频标签，短样本总媒体载荷约 1.1 Mbps |
| HLS fMP4 / AVC | 播放列表 HTTP 200，含 #EXTM3U，抽取的媒体分片 HTTP 200；尚未解码，也未验证持续更新 |
| HLS TS / AVC | 第一候选 CDN 的 TLS 连接失败；未关闭证书验证，未遍历全部备用 CDN |

FLV 元数据还含 videodatarate≈3321 kbps；它与短时媒体载荷测量不同，不能将这个字段作为持续真实码率。HEVC 只确认接口列出，未读取或解码。

biliup 与 LiveRecorder 的项目文档将 B 站高画质获取与登录 Cookie 联系起来，这支持将登录作为优先验证项，但不能证明当前账号在该房间必定取得原画。

## 斗鱼：用户指定房间号 6657

2026-10-06 更正：6657 是短号，当前网页主房间数据的真实房间号为 6979222。初次调查直接对 6657 调用播放接口，得到 error=-4 和旧 RoomApi 的未开播状态；这些返回对应错误的查询 ID，不能用来判断用户指定直播间的状态。用户使用原型遇到的 error=-3 也在转换真实房间号后消失。

修正后使用真实房间号参与签名并调用 getH5PlayV1，匿名请求 rate=0 实际返回 rate=4（蓝光4M）。短时样本为 H.264 HTTP-FLV、1920×1080、30 fps，视频标称 4000 kbps；本次约 5.47 秒媒体样本总载荷约 3.06 Mbps。上游会重定向到 livehwc4.com；加入这个已确认的 CDN 域名后，保持 HTTPS 证书校验，本机转发返回 HTTP 200 和有效 FLV 文件头。

这些结果确认匿名取流与短时转发可用；尚未完成该房间登录前后对比、实际音视频解码验收和长期稳定性测试。复测证据为 `.research/douyu-fix-2026-10-06.json`。

## 斗鱼：补充开播样本 36252

该样本为 MrGemini，公开接口显示正在直播。使用新播放接口、服务端 Date 时间计算请求参数，未携带账号 Cookie。

| 请求 | 接口实际返回 | 读取流元数据 |
|---|---|---|
| rate=0（原画请求） | 返回 rate=4 | 1920×1080、30 fps；视频标称 4000 kbps，音频标称 128 kbps；短样本总载荷约 3.18 Mbps |
| rate=3（超清请求） | 返回 rate=3 | 1280×720、30 fps；视频标称 2000 kbps，音频标称 128 kbps；短样本总载荷约 0.80 Mbps |

接口 multirates 同时列出“原画1080P60”约 10124 kbps、“蓝光4M”4000 kbps、“超清”2000 kbps、“高清”900 kbps。实际 rate=0 被返回为 rate=4，因此不能声称匿名拿到了 10 Mbps/60 fps 原画。

上述码率属于此样本及此次短时测试；实际编码可能是可变码率，元数据不保证等于实时平均值。请求 rate=0 被降档的原因，以及登录能否解锁原画，仍须同房间同时间段对比确认。

## 播放方式比较

| 方案 | 优点 | 需要解决的问题 | 建议 |
|---|---|---|---|
| 内置 libmpv | 播放、画质切换、状态和重连可在同一软件中管理；有嵌入 API、HTTP 请求头和缓存控制 | 引擎打包、窗口渲染、硬件解码、崩溃处理与分发许可 | 正式版优先评估 |
| 内置 libVLC / LibVLCSharp | 支持嵌入 Windows 应用；.NET 集成路线明确 | 同样需要引擎打包和实际流兼容性验证 | 若选 C#，可优先做对照原型 |
| 外部 PotPlayer | 用户沿用熟悉的播放器；软件先聚焦房间收藏、账号和解析 | 本机安装路径、进程控制、重开流、切换画质和播放器配置 | 原型首选，并保留为正式版选项 |
| Windows 默认播放器 | 已有系统应用，额外安装依赖较少 | 默认应用不确定；微软组件支持 HLS 不等于默认应用支持所有远程 URL、FLV、请求头和自动重连 | 后续选配，不作为主路径 |

Streamlink 当前源码有 PotPlayer 的启动参数适配，但这属于接入证据，不是本项目在 Windows 11 25H2 上的实播结果。微软 AdaptiveMediaSource 文档支持 HLS/DASH、自定义请求头及码率事件，适合评估系统内置播放组件；需要区分“内置微软组件”和“启动系统默认播放器”。

## 建议架构

房间收藏/历史 → 平台适配器 → 实际画质、编解码、候选 CDN、请求头和短期流地址 → 播放会话 → 内置播放器或本机转发 → PotPlayer。

- 平台适配器分别实现 B 站与斗鱼，避免播放器承担网页解析。
- 保存平台与房间 ID，每次打开重新解析直播流，不持久化过期的 CDN 地址。
- 画质 UI 使用实际返回档位；斗鱼检查返回 rate，B 站检查 current_qn，收到降档时向用户说明。
- 优先 AVC/H.264 兼容路径，HEVC 作为经验证的可选项。
- 内置播放可直接传递直播 URL 与必要请求头；外部播放优先评估仅绑定 127.0.0.1 的本机 HTTP 地址。
- 本机转发默认保持源编码，不转码、不永久保存直播内容。HLS 转发需同时处理播放列表、分片和初始化段。
- 转发 FLV 字节流并不会自动使其适配 Windows 默认播放器；需要时另行评估无重编码封装转换。
- 地址过期、HTTP 403/404、断流时重新解析并尝试备用 CDN；不要通过关闭 TLS 验证掩盖连接问题。
- 本机代理能集中处理登录态和请求头，但不能保证上游断流后播放器无缝恢复。

## 登录验证与下一轮验收

1. B 站本机交互登录后，验证登录态有效；对同一房间 35 再请求 qn=10000 与 400，检查 current_qn，再读取实际分辨率、帧率与码率。
2. 对斗鱼 6657（真实房间号 6979222）与开播样本 36252 登录前后请求 rate=0，核对返回 rate 与是否真正为 60 fps。
3. 账号会话仅在本机使用，凭据不进入报告、日志或播放器命令行；产品中评估扫码/内嵌登录与 Windows 凭据保护。
4. 使用内置引擎、PotPlayer、本机 HTTP 转发分别验证开流、声音、音画同步、全屏和清晰度切换。
5. 连续播放 30–60 分钟，统计开流耗时、缓冲、断流次数、重连恢复时间、CPU/GPU 和内存；测试断网恢复与地址刷新。
6. 只有上述数据成立后，才能报告“稳定播放”或“登录解锁最高画质”。
