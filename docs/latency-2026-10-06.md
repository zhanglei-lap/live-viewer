# 斗鱼 6657 延迟增长调查与 0.2.1

日期：2026-10-06（香港时间）。用户反馈 PotPlayer 最初比网页快，观看一段时间后落后，怀疑差值继续增加；房间为斗鱼 6657，中途没有手动暂停。当前用户暂时无法比较重新连接前后的差值，因此真实画面延迟增长尚未复现或定量确认。

2026-10-07 补充：用户报告已完成 30–60 分钟稳定性与断网恢复测试，均无明显问题；这是用户实测反馈。仍有 PotPlayer 重连后旧源残留与错误弹窗的交互问题，用户同意留待内置播放引擎阶段处理。

## 已观测

对 0.2.0 原转发链路匿名读取 90 秒，在第 15–75 秒观测到的“墙钟经过时间减 FLV 时间戳跨度”稳定在约 -6.38 秒，变化不足 0.03 秒。负值来自连接初始数据快速到达等因素，它不代表主播或网页的绝对延迟。

对 0.2.1 新链路同样读取 90 秒，采样时本工具收到与写出完整音视频标签的时间戳差为 0–0.15 秒；队列峰值约 56 KiB、约 0.001 秒，没有持续积压。这两次均由快速 HTTP 客户端读取，没有实际比较 PotPlayer 显示与平台网页，不能证明长时间播放器观看正常。

原链路同步读 CDN、写播放器，没有单独观察收到和写出的进度，也没有限制写播放器时阻塞的时长。若播放器消费变慢，这种结构可能将压力传回上游，形成旧数据积累；这只是机制上的可能性，不是已确认的用户问题原因。

## 本次修改

- 默认启用“优先实时播放”，上游读取与下游写入分开，FIFO 超过 8 MiB 或数据等待超过 3 秒时结束旧连接；本机写入设置 3 秒超时和较小发送缓冲。
- 正常连接原样按顺序转发；不会在同一 FLV 连接中丢掉任意字节或拼接新流，积压会提示点击“回到直播”。可关闭该选项恢复同步转发，下次播放生效。
- “回到直播”重新解析地址，使用本机 PotPlayer CmdLine64.txt 中支持的 /current /autoplay 选项在当前播放器重新打开流。不会修改播放器全局设置或自动改变播放速度。
- 增加完整 FLV 音视频时间戳观察，处理跨数据块、AVC/AAC 配置帧的零时间戳、32 位时间戳回绕和明显重置。此观察只用于统计，不更改视频数据。
- 报告 timing 包含收到与转发的媒体跨度、相对墙钟进度、收发进度差、最长写入时长、队列峰值与积压断开次数；明确标注 player_display_latency_measured=false。
- UI 显示“转发进度差”，并说明它不等于播放器画面延迟。新版 EXE 使用独立版本文件名，保留 0.2.0，沿用同目录 data 设置。

## 验证与限制

45 项自动化测试通过，包含字节顺序、时间戳分块/回绕/重置、队列超时与内存上限、取消唤醒、积压后不拼接备用流、普通模式字节一致性。两个平台的最终 EXE 取流与时间戳自检通过，观看页面截图已检查。

工具无法读取 PotPlayer 内部缓存长度或实际显示时间，也没有测量 CDN 到主播的绝对延迟。播放器内部缓冲、播放速度偏差或网页自己的追赶策略仍可能造成差异。浏览器播放库存在显式延迟追赶选项，例如 [mpegts.js 的 liveBufferLatencyChasing / liveSync](https://github.com/xqq/mpegts.js/blob/master/docs/api.md)；未确认斗鱼当前网页具体采用何种策略。

建议下次同时观察网页和 PotPlayer，确认播放速度为 1.0x，分别记下初始、5 分钟、15 分钟的画面差值。落后时记录状态栏转发进度差，点“回到直播”观察是否恢复，并在再次落后时导出报告。若转发进度差接近零、转发相对墙钟进度稳定而画面差增大，可进一步调查播放器缓冲或 CDN/网页播放策略；不能仅凭一个指标归因。
